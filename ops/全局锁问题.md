  ### 为什么 Caffeine 线程安全还不够？

  Caffeine 只能保证单个操作线程安全，例如：

  l1.peek(id);
  l1.remove(id);
  l1.put(fragment);

  但 Vortex 的准入是一个复合操作：

  1. 检查 fragment 是否已存在
  2. 检查 namespace quota
  3. 检查当前 token 容量
  4. 检查 pinned 工作集
  5. 必要时选择并删除 victim
  6. 插入新 fragment
  7. 更新 pin 索引和冷热 tier 索引

  每一步单独线程安全，不代表整个流程是原子的。

  ### 不加锁会发生什么？

  假设 L1 最大容量是100 tokens，当前已经使用80：

  线程 A：准备写入15 tokens
  线程 B：准备写入15 tokens

  没有锁时可能出现：

  A 读取当前容量：80，判断 80 + 15 <= 100，可以写
  B 读取当前容量：80，判断 80 + 15 <= 100，可以写
  A 写入，容量变成95
  B 写入，容量变成110

  即使 currentTokens 使用了 AtomicLong，它也只能保证最后准确记录为110，不能阻止容量超过100。

  加锁后：

  A 获得锁：检查80，写入后变成95，释放锁
  B 获得锁：重新读取95，发现需要释放10 tokens
  B 淘汰 victim，或者因为没有合适 victim 而拒绝准入

  这样容量约束才成立。

  ### 它具体保护哪些业务不变量？

  1. 防止容量超卖

  保证“检查容量”和“实际写入”之间不会插入另一个写线程。

  2. 防止两个线程重复选择同一个 victim

  假设两个线程都发现差5 tokens，如果并发执行，它们可能同时选择同一个 fragment：

  A：认为淘汰 X 可以释放5 tokens
  B：也认为淘汰 X 可以释放5 tokens

  最终 X 实际只释放一次，但两个线程都认为自己获得了空间，可能继续写入并超容量。

  3. 保证 namespace quota 判断有效

  配额计算依赖整个 L1 快照。如果计算完以后别的线程立刻写入同一个 namespace，刚才的判断就过期了。锁把“计算配额”和“提交写入”连在一起。

  4. 保证 pinned fragment 不会在并发变化中被误淘汰

  victim 选择需要读取 pin 状态。准入锁还覆盖相关的临时 fragment 删除、pin 状态刷新和索引更新，降低“刚被 pin，又被另一线程按旧状态淘汰”的竞态。

  5. 保持多份状态一致

  一次准入不只是修改 Caffeine，还要同步修改：

  L1 fragment
  currentTokens
  pin index
  hot/cold tier index
  eviction diagnostics

  如果执行到一半被其他线程观察，可能出现“L1里有数据但索引里没有”，或者“数据已经删除但 tier index 仍然存在”。锁让这些修改作为一个完整临界区执行。

  6. 防止整页准入被其他写入穿插

  Page Fault 可能一次回填多个 fragment。admitPage() 也使用同一把锁，使页面回填期间不会被其他准入操作穿插。不过这里的“原子”主要指不发生并发穿插，不表示所有 fragment 必然全部成功写
  入。

  ### 代价是什么？

  当前它是一把全局锁，不同 namespace 的写入也会串行：

  namespace A 写入 ─┐
  namespace B 写入 ─┼─ 竞争同一个 admissionLock
  namespace C 回填 ─┘

  而且锁内包含容量计算、候选扫描、语义打分、淘汰和索引更新。L2/L3 使用 persistAsync，不会同步等待 Milvus/MinIO 网络请求，但准入计算本身仍可能变重。
