  Vortex 项目问题分析与解决报告

  一、项目概述

  Vortex 是一个 AI Agent Memory & State Management Kernel，采用 Java 21 + Spring Boot 3.3 多模块 Maven
  架构。核心目标是实现 L1/L2/L3 三级层次化记忆 + 任务快照/恢复能力，面向 LLM Agent 场景。

  模块划分

  ┌────────────────┬────────────────────────────────────────────┬────────────────────────────────────────────────────┐
  │      模块      │                    职责                    │                       核心类                       │
  ├────────────────┼────────────────────────────────────────────┼────────────────────────────────────────────────────┤
  │ vortex-common  │ 领域模型 + DTO                             │ MemoryFragment, TaskState, RecallQuery,            │
  │                │                                            │ RecallResult                                       │
  ├────────────────┼────────────────────────────────────────────┼────────────────────────────────────────────────────┤
  │ vortex-storage │ L1/L2/L3 存储接口与实现                    │ CaffeineHotStore, MilvusWarmStore, MinioColdStore  │
  ├────────────────┼────────────────────────────────────────────┼────────────────────────────────────────────────────┤
  │ vortex-kernel  │ 核心编排：HMC、淘汰、切分、Embedding、快照 │ HierarchicalMemoryController,                      │
  │                │                                            │ SemanticEvictionPolicy, SnapshotService            │
  ├────────────────┼────────────────────────────────────────────┼────────────────────────────────────────────────────┤
  │ vortex-app     │ Spring Boot 入口、REST 控制器              │ MemoryController, TaskController                   │
  └────────────────┴────────────────────────────────────────────┴────────────────────────────────────────────────────┘

  技术栈

  - L1 热缓存：Caffeine（token 加权）
  - L2 向量检索：Milvus（IVF_FLAT + COSINE）
  - L3 冷存储/快照：MinIO
  - Embedding：本地 BGE-Small-ZH (512d) + 可选 DeepSeek Cloud (1024d)
  - 向量维度：默认 512（BGE-Small）

  阶段 0：初始评审发现的 P0 级问题（3 个）

  来源：项目评审.txt

  问题 0-1：L2 向量维度与运行时 Embedding 路径不一致

  问题发现：项目评审阶段首先指出。系统存在双轨道 Embedding（L1 用 BGE-Small 512d，L2 可用 DeepSeek 1024d），而 Milvus
  collection schema 的向量维度是固定的。一旦配置 embedding-dim: 1024 但运行时云 Embedding 未启用或失败，HMC 回退到本地
  512d，就会把 512 维向量写进 1024 维 collection。

  根本原因：配置层、模型层、Milvus schema 三者缺乏启动期一致性校验。application.yml 原始配置为 embedding-dim:
  1024，但本地 Embedding 默认只有 BGE-Small 512d。

  影响：
  - 轻则 upsert/search 失败
  - 重则召回结果不可预测，系统行为不一致

  解决方案（两层防护）：
  1. 配置层安全回退：application.yml:33 将 embedding-dim 默认改为 512，仅在明确启用云 Embedding 且完成 Milvus
  迁移时才切到 1024
  2. 启动期强校验：HierarchicalMemoryController.java:281 新增 validateL2DimensionCompatibility() 方法，比较
  l2.vectorDimension() 与实际生效的 Embedding 维度，不一致则直接 IllegalStateException 启动失败

  设计原则：Schema 级别不一致必须 fail-fast，不能靠运行时容错。

  当前状态：已修复

  ---
  问题 0-2：RecallQuery.tags 接口有定义但召回链路未真正过滤

  问题发现：DTO 层 RecallQuery.java:35 有 tags 字段，API 语义承诺"按标签过滤"，但 HMC 的 recall 流程只按 Embedding
  相似度召回，完全未使用 tags 条件。

  根本原因：接口定义与实现行为脱节。这是典型的"契约未兑现"问题。

  影响：
  - 用户想召回 role:user，实际会把 role:system 或其他任务片段也带回来
  - 语义污染，召回结果与预期不符

  解决方案（三级过滤）：
  1. L1 先过滤再排序：HierarchicalMemoryController.java:167，在缓存层直接按标签约束，避免返回错误标签的结果
  2. L2 二次校验：HierarchicalMemoryController.java:300，先从 L2 拿候选，再通过 L3 取完整 fragment，用 matchesAllTags()
  做最终过滤
  3. 搜索窗口放大：HierarchicalMemoryController.java:188，有标签时适当放大 L2 搜索窗口，因为过滤后有效结果变少

  设计原则：标签过滤属于"结果约束"而非"排序增强"，必须在最终返回前保证约束成立。

  当前状态：已修复，已有测试覆盖

  ---
  问题 0-3：Token 统计仍用启发式估算（char/3.5）

  问题发现：评审指出 SemanticTextSplitter.java:87-89 中 token 估算是 char / 3.5。

  根本原因：启发式估算与模型实际 tokenizer 不在同一尺度。中英混合、代码片段、标点密集文本下偏差极大。

  影响（三连击）：
  1. 切片大小失真——看起来 400 token，实际可能已超 512
  2. recall 的 tokenBudget 不可信——返回结果可能超预算或过早截断
  3. L1 容量管理失真——按 token 做容量控制但不是真 token，阈值判断漂移

  解决方案：
  - SemanticTextSplitter.java:30 注入真实 TokenCounter
  - 切分、存储、预算全部统一基于同一套 BGE tokenizer 的真实计数

  设计原则：Token 预算本质上是模型约束，不是文本长度约束，凡是和模型上下文窗口有关的地方都必须使用真实 tokenizer。

  当前状态：已修复

  阶段 1：代码审查发现的 4 个问题

  来源：当前问题.txt + 问题解决-claude.txt

  问题 1-1：importance 未参与淘汰评分计算

  问题发现：MemoryFragment.java:54 的 computeEvictionScore() 公式是 α*recency + β*similarity，importance
  字段虽然存在但完全没参与评分。

  根本原因：设计目标是三项加权，但实现时遗漏了第三个系数 γ。

  影响：语义淘汰退化为"recency + similarity"两维度，高重要性片段没有优先保留优势。

  解决方案：
  1. MemoryFragment.java:67 签名改为四参数 (queryEmbedding, alpha, beta, gamma)，公式变为 α*recency + β*similarity +
  γ*importance
  2. SemanticEvictionPolicy.java 新增 gamma 字段，默认值 0.2；beta 默认从 0.7 调整为 0.5，确保 α+β+γ=1.0
  3. application.yml 配置权重 α=0.3, β=0.5, γ=0.2

  当前状态：已修复

  ---
  问题 1-2：L2 回灌到 L1 时 Embedding 缺失（含修复过程中的逻辑回归）

  问题发现：MilvusWarmStore.java:145 构造 MemoryFragment 时未填充 embedding，但 HMC recall() 方法会将这些结果 l1.put(f)
  回灌到 L1。

  根本原因：Milvus search 返回的字段不包含 embedding 向量，构造 fragment 时遗漏了这一关键数据。

  影响：回灌到 L1 的 fragment 没有 embedding → 语义评分全部退化为 0 → L1 的淘汰和召回行为被削弱。

  第一次修复（错误）：直接在 MilvusWarmStore.search() 中用 queryEmbedding 填充 fragment 的 embedding 字段。

  逻辑回归发现：这个修复引入了更严重的问题——
  - 关闭云 embedding 时：fragment.embedding == queryEmbedding，所有 L2 命中的分数被抬成接近固定高分
  - 开启云 embedding 时：L2 查询向量是 1024 维，L1 查询向量是 512 维，余弦相似度直接返回 0.0
  - 更严重的是：错误向量会污染后续 L1 的淘汰和召回行为

  最终修复方案：
  1. MilvusWarmStore.search() 保持 embedding = null，不伪造向量
  2. HierarchicalMemoryController.java:184-187 回灌前补上 l1EmbeddingService.embed(f.getContent())，用 BGE-Small
  重新计算正确的 512d 向量

  设计原则：L2 不应返回虚假向量，回灌时必须用正确的 Embedding 模型重新计算。

  当前状态：已修复（经二次修正）

  问题 1-3：CaffeineHotStore L1 Token 计数漂移

  问题发现：当前问题.txt 已指出，问题解决-claude.txt 首次尝试修复后发现比表面更复杂。

  根本问题：put/remove 主流程和 Caffeine removalListener 同时在修改
  currentTokens，但不同移除场景行为不同，导致计数逻辑不统一。包含两个子问题：

  子问题 A：同 id 覆盖更新时 token 重复计算
  - 旧 fragment 10 token，新 fragment 25 token
  - 错误路径：put() 加差值 +15，但 cache.put() 替换旧值触发 listener 又减 -10
  - 结果：应该是 25，实际变成 15

  子问题 B：显式 remove 时双减
  - remove() 先手动减一次 currentTokens
  - cache.invalidate() 触发 removalListener 又减一次
  - 结果：token 计数被多减

  修复过程中的反复：
  - 第一次尝试把扣减逻辑全部交给 removalListener → 跑测试发现显式 invalidate 路径不触发 listener 扣减
  - 第二次拆分为显式删除手动扣减 + listener 负责非显式移除

  最终方案（三条路径责任清晰拆分）：
  1. removalListener（:45）：只处理 非 EXPLICIT 移除的 token 扣减（如容量淘汰触发的下沉）
  2. put()（:64）：更新时只加新值 token，替换旧值的扣减交给 listener 完成
  3. remove()（:89）：显式删除时先手动扣减，再 invalidate()
  4. clear(namespace)（:109）：不再直接 invalidate，统一走 remove()

  回归测试：
  - CaffeineHotStoreTest.java:11：同 id 更新后 token 总量应为新值
  - CaffeineHotStoreTest.java:20：显式删除后 token 总量归零

  当前状态：已修复

  问题 1-4：MilvusWarmStore.get() 空实现

  问题发现：MilvusWarmStore.java:181 的 get() 方法返回空实现。

  影响：存储接口未完全闭合，虽不影响主链路，但影响可测试性和未来扩展。

  修复过程中的编译错误：
  - 初始实现使用 new QueryResultsWrapper(result.getData().getFieldsData())
  - 编译报错：getFieldsData() 需要 int 参数，与实际 Milvus SDK 2.4.4 的 protobuf 生成 API 不匹配
  - 通过 Python 解压 jar 包，读取 class 字节码方法签名确认：
    - QueryResultsWrapper 构造函数实际接受 QueryResults 对象
    - 字段列表方法是 getFieldsDataList()（protobuf 风格），不是 getFieldsData()

  最终修复：
  1. 改为 new QueryResultsWrapper(result.getData())
  2. 使用 QueryParam + withExpr 按 id 精确查询
  3. 补充 import io.milvus.grpc.FieldData

  当前状态：已修复

  阶段 2：语义淘汰策略专项优化清单（阶段 1 执行）

  来源：阶段1.txt + 语义淘汰清单.txt

  问题 2-1：recency 24h 线性归零

  问题发现：MemoryFragment.java:75-79 的 recencyScore() 是线性衰减到 0，超过 24h
  的片段全部归零，两天前和两周前完全无差异。

  影响：淘汰算法对中长期记忆失去区分力。

  解决方案：改为对数衰减（log decay），超过 24h 后仍保留区分力。

  当前状态：已修复

  ---
  问题 2-2：recall 命中后不刷新 lastAccessTime

  问题发现：HMC recall 使用 getAll(namespace) 返回列表，不更新 lastAccessTime。刚被召回使用的片段 recency
  得分仍然很旧，容易被误淘汰。

  影响：频繁召回的片段不会被保护，反而可能被优先淘汰。

  解决方案：recall 改走 get(id) 而非 getAll()，确保被召回片段 recency 得分即时更新。

  当前状态：已修复

  ---
  问题 2-3：淘汰候选未按 namespace 隔离

  问题发现：淘汰候选为 getAllFragments() 全局候选，多会话场景下一个 namespace 的写入可能驱逐另一个 namespace 的热数据。

  影响：多租户场景下公平性无保障。

  解决方案：淘汰候选改为 getAllFragments(namespace)，禁止跨租户候选池合并。

  当前状态：已修复

  ---
  问题 2-4：候选池策略不稳定

  问题发现：预选"条目数前 10%"后再按 token 目标淘汰，当条目都很小时预选池可能不够，无法达到释放 token 目标。

  解决方案：废弃条目数前 10% 预选，改为按 score/tokenCount（价值密度）排序，确保释放量稳定达标。

  当前状态：已修复

  ---
  问题 2-5：importance 无动态更新机制

  问题发现：importance 默认值 0.5，业务未主动标注时 γ*importance 实际贡献有限。

  解决方案：在 recall 命中时动态提升 fragment 的 importance 值。answer-grounded
  回调接口暂未接入（仓库无现成入口），recall 路径的动态更新已落地。

  当前状态：部分修复（recall 路径已做，answer-grounded 回调待补）

  阶段 4：追加发现的 2 个问题

  来源：问题解决-claude.txt（修复过程中的 Findings）

  问题 4-1：SemanticEvictionPolicy 构造器测试未同步更新

  问题发现：gamma 参数加入后，SemanticEvictionPolicyTest.java:12 仍调用双参数构造器，编译直接失败。

  解决方案：改为三参数构造器 new SemanticEvictionPolicy(0.3, 0.5, 0.2)。

  当前状态：已修复

  ---
  问题 4-2：recall() L1/L2 结果未去重

  问题发现：同一个 fragment 在 storeFragment() 和逐出路径里都会被写入 L2，recall 时先取 L1 再追加 L2，未按 id 去重，导致
   token budget 被重复消耗。

  解决方案：L2 追加前收集 L1 结果的 id 集合 (seenIds)，跳过已命中的 fragment。

  当前状态：已修复

  四、关键工程教训与经验总结

  1. 修复可能引入新问题（问题 1-2 的教训）

  L2 回灌 Embedding 问题经历三次修改：
  - 第一次：用 queryEmbedding 填充（错误——语义污染）
  - 第二次：改用正确的构造函数（修复编译错误）
  - 第三次：在 HMC 层重新 Embed（正确方案）

  教训：修复一致性问题时，不能只看"当前缺失"，还必须追溯数据在后续链路中的使用方式，防止修复本身引入语义回归。

  2. Listener 与手动逻辑的职责冲突（问题 1-3 的教训）

  CaffeineHotStore 的 token 计数问题经历了多轮修改：
  - 先尝试"全部交给 listener"→ 不行（显式 invalidate 路径行为不同）
  - 再拆分为三条路径分别处理

  教训：事件驱动框架（如 Caffeine listener）的回调时机和覆盖范围需要实际验证，不能仅靠代码推演。

  3. SDK API 签名不能靠文档推断（问题 1-4 的教训）

  Milvus SDK 2.4.4 的 QueryResultsWrapper 构造函数和字段访问方法与文档/直觉不符，需要通过反编译 jar
  包字节码确认真实签名。

  教训：使用第三方 SDK 时，应先通过测试或反编译确认 API，而不是假设文档/接口签名一定正确。

  4. 环境一致性是隐性杀手（问题 5）

  pom.xml 要求 Java 21，但系统默认 Maven 绑定 JDK 17，导致 invalid target release: 21 错误。这不是代码
  bug，但会导致误判。

  教训：多模块项目应显式在 CI 和 README 中声明 JDK 版本要求。
