  二、问题 1：L2 向量维度与运行时 embedding 路径可能不一致

  发现方式

  这是评审里最先指出的 P0 问题。它的本质不是某一行代码写错，而是“配置、模型、Milvus schema”三者之间可能不一致。

  当前已经能看到修复痕迹：

  - vortex-app/src/main/resources/application.yml:33 把 embedding-dim 默认改成了 512
  - vortex-kernel/src/main/java/com/vortex/kernel/hmc/HierarchicalMemoryController.java:281 增加了
  validateL2DimensionCompatibility()

  问题原因

  系统里实际存在两套 embedding 路径：

  - L1 本地 BGE：512 维
  - L2 云 embedding：1024 维

  而 Milvus collection 的向量字段维度是固定 schema，一旦建库时是 1024，后面就不能直接塞 512 维向量。

  所以只要出现下面这种情况，就会出问题：

  - 配置上 L2 collection 按 1024 维建立
  - 运行时云 embedding 没启用或者失败
  - HMC 回退到本地 512 维 embedding
  - 最终把 512 维向量写进 1024 维 collection

  结果就是：

  - 轻则 upsert/search 失败
  - 重则系统行为不一致，召回结果不可预测

  解决方案

  当前代码的解决策略是对的，分两层：

  1. 配置层默认安全回退
      - vortex-app/src/main/resources/application.yml:33 默认使用 512
      - 只有明确启用云 embedding 并完成 Milvus 迁移时，才切到 1024
  2. 启动期做强校验
      - vortex-kernel/src/main/java/com/vortex/kernel/hmc/HierarchicalMemoryController.java:281 会比较：
          - l2.vectorDimension()
          - 当前实际生效的 embedding 维度
      - 一旦不一致，直接 IllegalStateException 启动失败

  为什么这个方案正确

  因为这个问题不能靠“运行时尽量容错”解决，必须 fail-fast。
  这是 schema 级别不一致，不是业务参数误差。晚失败比早失败更危险。

  当前状态

  这个问题在当前代码里已经补上了，属于“评审指出，代码已修”。

  三、问题 2：RecallQuery.tags 接口有定义，但召回链路未真正执行过滤

  发现方式

  评审指出接口承诺和实际行为不一致。检查当前 HMC 后，我确认这部分现在已经接进来了：

  - 标签归一化：vortex-kernel/src/main/java/com/vortex/kernel/hmc/HierarchicalMemoryController.java:312
  - L1 过滤：vortex-kernel/src/main/java/com/vortex/kernel/hmc/HierarchicalMemoryController.java:167
  - L2 补充过滤：vortex-kernel/src/main/java/com/vortex/kernel/hmc/HierarchicalMemoryController.java:300
  - 标签匹配逻辑：vortex-kernel/src/main/java/com/vortex/kernel/hmc/HierarchicalMemoryController.java:324

  问题原因

  原始问题的根本原因是：

  - DTO 里有 tags
  - API 语义已经承诺“按标签过滤”
  - 但 recall 流程只按 embedding 相似度召回，没有执行标签约束

  这会造成很典型的语义污染：

  - 用户想召回 role:user
  - 实际把 role:system 或其他任务片段也带回来了

  这类问题不一定报错，但业务语义已经错了。

  解决方案

  当前代码的处理方式是合理的：

  1. L1 先按标签过滤，再做相似度排序
     这样缓存层不会直接返回错误标签的结果。
  2. L2 因为向量检索结果不一定带完整标签，所以做二次校验
      - 先从 L2 拿候选
      - 再通过 L3 取完整 fragment
      - 用 matchesAllTags() 做最终过滤
  3. 有标签时适当放大 L2 搜索窗口
      - vortex-kernel/src/main/java/com/vortex/kernel/hmc/HierarchicalMemoryController.java:188
      - 因为过滤后有效结果会变少，不放大搜索窗口容易召不满

  为什么这个方案正确

  因为标签过滤不属于“排序增强”，而属于“结果约束”。
  必须在最终返回前保证约束成立，而不能只依赖向量检索初筛。

  四、问题 3：token 统计如果用启发式估算，会直接影响切片、预算和淘汰

  发现方式

  评审指出早期实现是 char / 3.5 这种启发式估算。
  我检查当前实现后确认已经换成真实 tokenizer 计数：

  - SemanticTextSplitter 注入 TokenCounter：vortex-kernel/src/main/java/com/vortex/kernel/hmc/
  SemanticTextSplitter.java:30
  - 真正计数入口：vortex-kernel/src/main/java/com/vortex/kernel/hmc/SemanticTextSplitter.java:89
  - 分块过程中实际用这个计数：vortex-kernel/src/main/java/com/vortex/kernel/hmc/SemanticTextSplitter.java:53
  - buildFragment() 里保存的 tokenCount 也是实计值：vortex-kernel/src/main/java/com/vortex/kernel/hmc/
  SemanticTextSplitter.java:79

  问题原因

  启发式 token 估算的问题在于，它和模型实际 tokenizer 不是同一个尺度。

  影响有 3 个：

  1. 切片大小会失真
     看起来 400 token，实际可能已经超 512。
  2. recall 的 tokenBudget 不可信
     返回结果可能超预算，或者过早截断。
  3. L1 容量管理会失真
     因为 L1 是按 token 做容量控制，不是真 token 就会导致阈值判断漂移。

  解决方案

  现在的修法是对的：

  - 让 SemanticTextSplitter 直接依赖 TokenCounter
  - 让 token 计数和 embedding 模型使用同一套 tokenizer 家族
  - 切分、存储、预算都统一基于这一套真实 token 计数

  为什么这个方案正确

  因为 token 预算本质上是模型约束，不是文本长度约束。
  凡是和模型上下文窗口有关的地方，都应该使用真实 tokenizer。

  当前状态

  这个问题当前也已经修好。

  五、问题 4：L1 currentTokens 统计会漂移，这是我这次实际发现并修掉的问题

  这是这次最重要的新增发现。

  发现方式

  我不是先从代码里百分百确认的，而是分两步发现：

  1. 先从 当前问题.txt 看到了你之前已经意识到 L1 token 计数有问题
  2. 我继续为它补了回归测试，并真正跑起来后，确认这个问题确实存在，而且比表面更复杂

  新增测试在：

  - vortex-storage/src/test/java/com/vortex/storage/l1/CaffeineHotStoreTest.java:10

  问题现象

  currentTokens 是 L1 当前 token 占用量，它直接影响：

  - 是否触发 evictionThreshold
  - maybeEvict() 判断是否接近容量上限
  - 整个 L1 负载是否准确

  如果这个值漂移，后果会是：

  - 明明没满却触发淘汰
  - 明明超了却不淘汰
  - 长时间运行后容量感知越来越不准

  问题原因

  这个 bug 的本质是：
  put/remove 主流程和 Caffeine removalListener 同时都在改 currentTokens，但不同移除场景行为不一样，导致计数逻辑不统一。

  具体分成两个子问题。

  子问题 A：同 id 覆盖更新时，旧 token 和新 token 会重复参与计算

  假设旧 fragment 是 10 token，新 fragment 是 25 token。

  错误思路会是：

  - put() 里手动只加差值 +15
  - 但 cache.put() 替换旧值时，removalListener 又会把旧值 -10

  最后得到：

  - 原本应该是 25
  - 实际可能变成 15

  也就是旧值被算了两次。

  子问题 B：显式 remove 时，不能再依赖 listener 统一扣减

  我最开始也尝试过“把扣减逻辑全部交给 removalListener”，但真正跑测试后发现不成立：

  - 显式 invalidate() 这条路径，不适合再依赖统一 listener 扣减
  - 否则 currentTokens 可能保持原值不变

  这个现象我是通过测试直接复现出来的，不是猜的。

  解决方案

  最终修法在 vortex-storage/src/main/java/com/vortex/storage/l1/CaffeineHotStore.java:43：

  1. removalListener 只处理非 EXPLICIT 移除的 token 扣减
      - vortex-storage/src/main/java/com/vortex/storage/l1/CaffeineHotStore.java:45
  2. put() 更新时只加“新值 token”
      - vortex-storage/src/main/java/com/vortex/storage/l1/CaffeineHotStore.java:64
      - 替换旧值带来的旧 token 扣减，交给 replacement 触发的 listener 完成
  3. remove() 显式删除时，先手动扣减，再 invalidate()
      - vortex-storage/src/main/java/com/vortex/storage/l1/CaffeineHotStore.java:89
  4. clear(namespace) 不再直接 invalidate，而是统一走 remove()
      - vortex-storage/src/main/java/com/vortex/storage/l1/CaffeineHotStore.java:109

  为什么这个方案正确

  因为现在 3 条路径的责任被拆清楚了：

  - 显式删除：调用方负   扣减
  - 替换旧值：listener 负责回收旧值
  - Caffeine 自身淘汰：listener 负责回收并触发下沉

  这就避免了“有的路径重复减，有的路径没减”的混乱。

  验证结果

  我补了两个回归测试：

  - vortex-storage/src/test/java/com/vortex/storage/l1/CaffeineHotStoreTest.java:11
      - 验证同 id 更新后 token 总量应为新值，而不是漂移值
  - vortex-storage/src/test/java/com/vortex/storage/l1/CaffeineHotStoreTest.java:20
      - 验证显式删除后 token 总量归零

  这两个测试都通过了。
