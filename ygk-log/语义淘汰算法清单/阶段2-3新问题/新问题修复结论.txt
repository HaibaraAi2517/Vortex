● 评审分析

  问题发现质量

  发现清单质量不错，6 个问题分了三个优先级，逻辑清晰。不过：

  - B-1 误判了 — FileBackedProcessedTaskStore 本来就有 maxEntries 裁剪，属于没读代码就下结论
  - B-3 偏理论化 — 描述的"清除 pin 后应重新评分"在实际场景中触发概率极低，属于边界 case 的边界 case
  - B-2、B-4、B-5 是真问题，性能上的 O(n) 和 O(n²) 确实值得修

  修复质量

  修复方案整体务实且到位，具体来说：

  1. Pin 过期清理改到期队列 — 正确选择。用 PriorityQueue + deadline map 替代全量扫描，从 O(n) 降到 O(k)（k =
  到期数量），而且实现比原文建议的 ConcurrentSkipListSet 更简洁
  2. Pin 操作分离 recency 访问 — put(fragment, recordAccess) + peek(id) 这个设计很好，说明真正理解了 LRU
  的语义：维护操作不应污染访问热度。这比原问题描述（B-3）的修复方案更本质
  3. Namespace token 预计算 — 标准的"缓存计算结果，避免重复扫描"手法，干净利落
  4. Recall 冗余度预计算 — RedundancyStats 一次算完复用，把 O(n²) 的重复扫描降到一次

  四个修复都没有过度设计，改动集中在 HMC 一个类里，测试覆盖也合理。

  关于引入 Redis 或 MQ

  当前阶段完全没必要。 理由如下：

  1. Pin 到期是纯内存操作 — 到期队列在 JVM 内就能高效解决，没有跨进程需求
  2. B-6 的并发安全问题 — DLQ replay 本身就是单线程 + idempotency key，引入 Redis/MQ
  只是把单线程保证从代码层移到了基础设施层，复杂度收益比为负
  3. 项目定位是 MVP/portfolio — Redis 已经用于 L2 向量存储，再为 pin 管理引入 Redis ZSET 属于架构升级过早
  4. MQ 延时队列杀鸡用牛刀 — pin 的 TTL 通常是分钟级，30 秒扫描一次到期队列完全够用

  什么时候值得考虑：
  - 如果未来要做分布式多实例部署（多 JVM 共享 pin 状态）
  - 如果 pin fragment 数量达到十万级以上
  - 如果需要跨服务的事件驱动 pin 失效

  目前这些条件都不满足，现有方案是正确的选择。
