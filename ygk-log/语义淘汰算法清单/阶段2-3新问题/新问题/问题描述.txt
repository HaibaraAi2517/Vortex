---
  专家审评：四个修复的漏洞分析

  修复 1：Pin 到期队列 — 有两个小问题

  问题 A：队列中 stale entries 无限累积

  indexPin() 每次被调用都 offer() 新条目，旧条目不从队列移除：

  // HMC:768 — 只 offer，不删旧的
  pinExpirations.offer(new PinnedFragmentRef(fragment.getId(), pinnedUntil));

  clearExpiredPins() 靠 deadline map 比对来跳过旧条目（第 383 行），功能正确。但如果调用方对同一 fragment 反复
  pin/unpin，队列中会堆积大量 stale entry。极端场景下（比如测试循环 pin 1000 次），队列可能有 1000 条实际只有 1 个有效
  entry。

  建议： 这是惰性清理策略的已知代价，实际场景中 pin 频率不高，可以接受。如果要根治，在 unpinFragment() 时增加一个
  tombstone set，clearExpiredPins() 遇到时跳过并清理。

  问题 B：clearExpiredPins() 不是线程安全的原子操作

  @Scheduled 和 maybeEvict() / enforceQuotaBeforeInsert() 都会调用 clearExpiredPins()。虽然 PriorityBlockingQueue 和
  ConcurrentHashMap 各自线程安全，但 clearExpiredPins() 的 逻辑组合不是原子的：

  // 线程 A (Scheduled) 正在执行 clearExpiredPins()
  // 线程 B (store 请求) 也调用了 clearExpiredPins()
  // 两者同时 peek() 同一个 ref，都 poll() 了它
  // → 同一个 fragment 的 pin 被"清除"两次（第二次 clearExpiredPin() 返回 false，无害）

  严重度：极低。 第二次清除时 clearExpiredPin() 返回 false，只是浪费一次 findFragment() + l1.put()
  调用。不会导致数据错误。但如果是高频并发 store，这个重复工作量会累积。

  ---
  修复 2：Pin/Recency 分离 — 有一个隐蔽的语义问题

  问题：l1.put(found, false) 虽然不刷新 lastAccessTime，但会替换 Caffeine 中的对象引用。

  // pinFragment() 第 351 行
  l1.put(found, false);  // put 会调用 cache.put()，替换旧值

  Caffeine 的 cache.put() 会触发 removalListener 对旧值执行回调（减 token），然后放入新值（加 token）。虽然 fragment
  对象本身不变，但 Caffeine 内部的权重统计经历了一次 remove + add 循环。在极端并发下，这可能导致 currentTokens
  短暂波动。

  严重度：极低。 单线程看是安全的，因为 currentTokens 用的 AtomicLong，加减是原子的。只是概念上不够干净——理想情况应该用
  cache.asMap().compute() 来做原地更新，避免 removal 触发。

  ---
  修复 3：Namespace token 预计算 — 有一个正确性漏洞

  问题：computeNamespaceTokenUsage() 的输入 candidates 只包含当前 namespace 的片段，但 map 被传入了可能跨 namespace
  操作的 evictCandidateGroup()。

  // maybeEvict() 第 419 行
  List<MemoryFragment> candidates = new ArrayList<>(l1.getAll(namespace));  // 只有当前 namespace
  // 第 427 行
  Map<String, Long> namespaceTokenUsage = computeNamespaceTokenUsage(candidates);  // map 只有一个 namespace 的 key

  evictCandidateGroup() 第 569 行：

  long currentNamespaceTokens = namespaceTokenUsage.getOrDefault(namespace, 0L);

  这里 namespace 是从 candidate.fragment().getNamespace() 获取的——在 maybeEvict() 路径中，所有候选都属于同一个
  namespace，所以实际不会出问题。

  但代码有一个隐含假设：maybeEvict() 只淘汰当前 namespace 的片段。如果未来有人修改代码让 maybeEvict() 也跨 namespace
  淘汰，这个假设就会破掉。目前是安全的，但缺乏防御性。

  ---
  修复 4：Recall 冗余度预计算 — 这是最重要的漏洞

  问题：L2 结果回填时，computeRedundancyStats() 被重复调用且参数不一致。

  看第 282-288 行：

  // 每从 L2 取回一个 fragment，都重新算一次
  Map<String, RedundancyStats> updatedStats = computeRedundancyStats(
      appendCandidate(filteredL1Candidates, candidate));  // ← O(n²)
  double score = scoreForRecall(candidate, l1QueryEmbedding, profileSelection.active(), updatedStats);
  // ...
  filteredL1Candidates = appendCandidate(filteredL1Candidates, candidate);  // ← 扩大候选池

  修复文件说"rankForRecall 不再为每个 fragment 重新流式扫描"——这对 L1 排序是正确的（第 628 行只算一次）。但在 L2
  回填路径中，每取回一个 L2 fragment 就重新调用 computeRedundancyStats()，而且每次传入的候选池都在增长。

  如果 L1 有 50 个 fragment，L2 回填 10 个：
  - 第 1 次：对 51 个 fragment 算 O(51²)
  - 第 2 次：对 52 个 fragment 算 O(52²)
  - ...
  - 第 10 次：对 60 个 fragment 算 O(60²)

  总开销 = O(51² + 52² + ... + 60²) ≈ 10 × 55² = 30,250 次余弦计算。而修复前是每个 L2 候选算一次
  O(n²)，修复后反而更重了。

  严重度：中。 这是修复引入的性能回退。原来 rankForRecall() 的 O(n²) 问题确实修好了，但 L2 路径引入了更糟的重复计算。

  修复建议： L2 回填路径应该像 L1 一样，维护一个累计的 RedundancyStats，每加入新 fragment
  时增量更新，而不是每次全量重算。

  ---
  整体架构层面的漏洞

  漏洞 1：Caffeine 自身淘汰 vs Semantic 淘汰的竞态

  Caffeine 的 maximumWeight 配置了 token 上限，当 weight 超限时 Caffeine 自己也会淘汰 fragment（Window-TinyLFU）。HMC 的
   maybeEvict() 是主动淘汰，Caffeine 的淘汰是被动淘汰。

  两者可能同时发生：

  线程 A: maybeEvict() → 选择 f-005 淘汰 → l1.remove("f-005")
  线程 B: Caffeine 内部 → weight 超限 → 淘汰 f-005 → 触发 removalListener

  l1.remove() 调用 cache.invalidate()（第 111 行），这是显式移除，Caffeine 的 RemovalCause 是 EXPLICIT，listener 中 不会
   重复减 token（第 45-47 行正确跳过了 EXPLICIT）。但如果 Caffeine 先触发了被动淘汰（cause !=
  EXPLICIT），handleCaffeineEviction() 会执行一次额外的异步 persist，而 evictCandidateGroup() 也会 persist 同一个
  fragment——双重 persist。

  严重度：低。 persistAsync 对 Milvus/MinIO 的 upsert 是幂等的，不会产生错误数据，只是浪费一次 IO。

  漏洞 2：pin 对 Caffeine 内部淘汰无效

  pin 机制在 HMC 层面拦截了 SemanticEvictionPolicy 的淘汰，但无法拦截 Caffeine 自身的 weight-based 淘汰。

  当 Caffeine 的 maximumWeight 超限时，Caffeine 的 Window-TinyLFU 算法会自己选择淘汰对象——它不知道 fragment 是否被
  pin。一个 pinned fragment 可能被 Caffeine 被动淘汰。

  // CaffeineHotStore 的 removalListener — 只检查 cause，不检查 pin
  .removalListener((String k, MemoryFragment v, RemovalCause cause) -> {
      if (cause.wasEvicted()) {
          evictionListener.accept(v, cause);  // ← 不管是否 pinned
      }
  })

  handleCaffeineEviction() 会把这个 pinned fragment 推到 L2/L3，而 clearExpiredPins() 之后在 pinnedFragmentDeadlines
  中找不到它了（已被 invalidate）。

  严重度：高。 这是 pin 机制的根本性漏洞。一个被 pin 的 fragment 如果 L1 总 weight 超限，Caffeine 会无视 pin
  直接淘汰它。

  修复方案：
  - 方案 A：Caffeine maximumWeight 设得比实际 token 容量大（比如 120%），让 HMC 的 maybeEvict() 始终在 Caffeine
  之前触发，Caffeine 的被动淘汰只作为最后防线
  - 方案 B：在 Caffeine 的 removalListener 中检查 v.isPinned()，如果是 pinned 且 cause 是 weight overflow，就把 fragment
   重新 cache.put() 回去（但可能触发无限循环，需谨慎）
  - 方案 C：将 Caffeine 的 maximumWeight 设为 Long.MAX_VALUE（无上限），完全由 HMC 控制淘汰节奏
