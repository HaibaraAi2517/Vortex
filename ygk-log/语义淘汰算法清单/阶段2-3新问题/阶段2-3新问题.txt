新发现的问题

  🔴 B-1: FileBackedProcessedTaskStore 无界增长（高）

  application.yml 配置了 processed-keys.max-entries: 10000，但如果 FileBackedProcessedTaskStore 的实现中没有使用该值做
  LRU 淘汰或定期清理，markProcessed() 会无限积累 key，最终导致内存或磁盘溢出。

  建议: 确认 FileBackedProcessedTaskStore 实现了基于 max-entries 的容量限制（如 LRU eviction 或 circular
  buffer）。如果尚未实现，这是一个必须修复的问题。

  🟡 B-2: clearExpiredPins() 扫描效率问题（中）

  @Scheduled(fixedDelayString = "${vortex.kernel.pin.cleanup-interval-ms:30000}")
  public void clearExpiredPins() {
      // 遍历 L1 所有 fragment，调用 clearExpiredPin()
  }

  当前实现遍历 L1 所有 fragment 来查找已过期的 pin。如果 L1 中有大量非 pinned fragment，这是 O(n) 的无谓扫描。

  建议: 维护一个 ConcurrentSkipListSet<MemoryFragment> 或 PriorityQueue 按 pinnedUntil 排序，只扫描到期的
  fragment。短期可以接受，但 L1 规模增大后会成为瓶颈。

  🟡 B-3: resolveEvictionGroup() 单片段路径 pin 检查后无重新评分（中）

  // line 554-561
  if (candidate.getReasoningChainId() == null) {
      clearExpiredPin(candidate);  // 可能清除pin
      if (candidate.isPinned()) return;  // 仍被pin则跳过
      // ... 直接返回单片段
  }

  clearExpiredPin() 可能清除过期 pin，但之后 isPinned() 只检查 pinnedUntil > now。如果刚清除的 pinnedUntil 恰好在 clear
  和 isPinned 之间的微秒窗口过期，这里不会有问题（因为 clear 已经设为 null）。但逻辑上，清除过期 pin 后应该重新评估该
  fragment 的淘汰分数，因为它之前可能因 pin 被跳过了多轮，现在突然变为可淘汰状态。

  建议: 清除过期 pin 后，将该 fragment 重新加入候选池而非直接返回，确保不遗漏。

  🟡 B-4: evictCandidateGroup() 中重复扫描 L1 计算命名空间 token（中）

  // line ~530-536 in evictCandidateGroup()
  long currentNamespaceTokens = l1.getAll().values().stream()
      .filter(f -> f.getNamespace().equals(namespace))
      .mapToLong(MemoryFragment::getTokenCount)
      .sum();

  每次调用 evictCandidateGroup() 都重新扫描 L1 计算当前命名空间的 token
  总量。在组淘汰循环中，如果一组被淘汰后触发另一组淘汰，会重复 O(n) 扫描。

  建议: 将 currentNamespaceTokens 作为参数传入，或使用 NamespaceQuotaManager 缓存的 snapshot 值。

  🟢 B-5: rankForRecall() 的 O(n²) 冗余度计算（低）

  private List<ScoredCandidate> rankForRecall(List<MemoryFragment> candidates, ...) {
      for (MemoryFragment fragment : candidates) {
          // 对每个 fragment，计算与所有其他 fragment 的 redundancy/novelty
          for (MemoryFragment peer : candidates) { ... }
      }
  }

  recall 时对 N 个候选片段执行 O(n²) 的 redundancy/novelty 计算。当 recall 返回大量片段时（如 top
  50），这个开销不可忽视。

  建议: 这与淘汰阶段的同类问题一致。对于 recall 场景，可考虑：
  - 只对 top-K（如 top 20）计算冗余度
  - 或在 recall 场景中忽略 redundancy/novelty（这些主要为淘汰设计）

  🟢 B-6: persistTask() L2/L3步骤幂等性仍非并发安全（低）

  if (!task.isL2Persisted() && fragment.getEmbedding() != null) {
      l2.upsert(fragment);
      task.setL2Persisted(true);  // 对象级别标记，非持久化
  }

  isL2Persisted/isL3Archived 是内存中的标记。如果同一任务被两个线程同时从 DLQ 重放，两者可能都读到 isL2Persisted=false
  并同时执行 upsert。Milvus upsert 本身是幂等的（相同主键覆盖），所以实际影响有限。但如果 l3 不幂等，可能产生重复归档。

  影响极低，因为 DLQ replay 本身是单线程的（replay() 按序执行），且有 processedTaskStore.contains() 检查。
