● 你的直觉是对的——推理进行中，项目中实际上没有主动保护推理链不被淘汰。

  现有保护机制的实际效果

  我上面推演中说"推理链组分高所以不会被淘汰"，但那不是硬保证，只是概率上的有利：

  推理链组的保护 = density 较高 → 排在淘汰候选列表的后面
                   ↓
              但如果 L1 真的很满，需要淘汰的 token 很多
                   ↓
              低分的被淘汰完了还不够
                   ↓
              推理链组也会被淘汰（整组一起降级到 L2/L3）

  也就是说：

  ┌───────────────────────┬─────────────────────────────────────┬──────────────────────────────────────┐
  │         机制          │        能保护推理进行中吗？         │                 原因                 │
  ├───────────────────────┼─────────────────────────────────────┼──────────────────────────────────────┤
  │ reasoningChainId 分组 │ 不能                                │ 它只是让组内"同生共死"，不阻止被淘汰 │
  ├───────────────────────┼─────────────────────────────────────┼──────────────────────────────────────┤
  │ 语义相似度 β=0.5      │ 不一定                              │ 和当前查询相似的分高，但不是防淘汰   │
  ├───────────────────────┼─────────────────────────────────────┼──────────────────────────────────────┤
  │ pin TTL               │ 能，但需要调用方主动传 pinTtlMillis │ 不传就没有                           │
  └───────────────────────┴─────────────────────────────────────┴──────────────────────────────────────┘

  项目中的设计缺口

  项目没有以下机制：

  - 没有 "推理进行中"状态标记（如 activeChainIds 集合）
  - 没有 淘汰时检查"该推理链是否仍在活跃推理中"
  - 没有 调用方注册/注销推理链生命周期的 API

  保护推理链不被淘汰完全依赖调用方自己传 pinTtlMillis。如果调用方忘了传，推理链在 L1 压力大时随时可能被整组降级到
  L2/L3。

  这合理吗？

  取决于你对这个项目的定位：

  作为记忆内核（当前设计）— 可以接受。理由是：
  - Vortex 是被动的存储层，不知道"推理是否正在进行"
  - reasoningChainId 是分组机制，不是保护机制
  - pin 是保护机制，但由调用方按需使用

  如果要做成"AI 推理保障层"— 不够。缺少的是：

  POST /api/v1/memory/chain/activate    // "我在推理了，别动这个链"
  POST /api/v1/memory/chain/deactivate  // "推理完了，可以正常淘汰了"

  这两个 API 会维护一个 Set<String> activeChainIds，淘汰时检查：

  // 缺失的逻辑（伪代码）
  if (activeChainIds.contains(groupId)) {
      return 0;  // 推理进行中，跳过
  }

  简单说：当前项目把"推理保护"的责任完全推给了调用方，自己没有感知推理生命周期的能力。 对于 MVP 这够用，但如果要让 LLM
  agent 真正放心地长推理，应该补上这个。

❯ pin是怎么被调用方使用的？调特定的api吗

● 对，有两种方式。让我直接指出具体的 API 和参数。

  方式一：store 时顺带 pin

  在 POST /api/v1/memory/store 的请求体里多传一个 pinTtlMillis：

  {
    "content": "用户需要设计电商系统数据库...",
    "namespace": "agent-session-001",
    "tags": ["role:assistant"],
    "reasoningChainId": "task-db-design-a1b2c3d4",
    "pinTtlMillis": 300000
  }

  300000 毫秒 = 5 分钟，这个 fragment 从存入那一刻起 5 分钟内不可被淘汰。

  方式二：事后单独 pin/unpin

  两个独立的 API：

  POST /api/v1/memory/pin
  {
    "fragmentId": "f-001",
    "pinTtlMillis": 120000       // pin 2 分钟
  }

  POST /api/v1/memory/unpin
  {
    "fragmentId": "f-001"        // 立即解除 pin
  }

  调用时序示例

  AI 推理开始
      │
      ├─ POST /store { content: "推理起点...", reasoningChainId: "chain-A", pinTtlMillis: 600000 }
      │     → f-001 被 pin 10 分钟（锚点，硬保护）
      │
      ├─ POST /store { content: "步骤2...", reasoningChainId: "chain-A", pinTtlMillis: null }
      │     → f-002 没有 pin，靠 chainId 分组保全
      │
      ├─ POST /store { content: "步骤3...", reasoningChainId: "chain-A", pinTtlMillis: null }
      │     → f-003 同上
      │
      ├─ POST /pin { fragmentId: "f-003", pinTtlMillis: 30000 }
      │     → 临时 pin 住最新的步骤，给自己留 30 秒缓冲
      │
  AI 推理结束
      │
      ├─ POST /unpin { fragmentId: "f-001" }
      │     → 主动解除，不再占用 pin 名额

  问题在哪

  这要求调用方自己算好时机：

  - pinTtlMillis 太短 → 推理还没结束 pin 就过期了，fragment 被淘汰
  - pinTtlMillis 太长 → 长期霸占 L1 空间，其他 fragment 被挤掉
  - 忘了传 → 完全没有保护
  - 忘了 unpin → 浪费 pin 名额

  本质上是调用方在手动管理一段应该自动化的生命周期。这就是前面说的缺口——项目缺少一个"注册活跃推理链 →
  推理结束后自动释放"的机制。
