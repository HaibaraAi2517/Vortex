  #8 下沉链路幂等 & 可重放 — 审查结论：🟡 基本达标，有设计缺陷

  问题 8-A（中等）：persistTask() 中 L2 和 L3 写入不是原子的

  FragmentPersistenceManager.java:89-103

  private void persistTask(FragmentPersistenceTask task) {
      if (processedTaskStore.contains(task.getIdempotencyKey())) {  // 1. 检查幂等
          return;
      }
      MemoryFragment fragment = task.getFragment();
      if (fragment.getEmbedding() != null) {
          l2.upsert(fragment);          // 2. 写 L2
      }
      l3.archiveFragment(fragment);     // 3. 写 L3
      processedTaskStore.markProcessed(task.getIdempotencyKey()); // 4. 标记完成
  }

  问题：如果步骤 2（L2 upsert）成功，步骤 3（L3 archive）抛异常，会进入 persistOrEnqueue() 的 catch 块并放入 DLQ。但下次
   replay 时，步骤 1 检查 processedTaskStore.contains() 会返回 false（因为还没 markProcessed），所以会重复执行 L2
  upsert。

  - L2 用 Milvus upsert，重复写入是幂等的，不会出错
  - L3 用固定 key 覆盖写，重复写入也是幂等的
  - 所以这个设计依赖底层存储的结果幂等性来保证正确性，而不是严格的过程幂等

  影响：当前 L2/L3 实现碰巧是幂等的，但如果将来换存储引擎或写入逻辑变化，这个假设就会破裂。

  严重性：中等（当前可工作，但架构脆弱）

  问题 8-B（中等）：FileBackedProcessedTaskStore 无清理机制，文件会无限增长

  FileBackedProcessedTaskStore.java 的 markProcessed() 只做
  append，没有任何过期清理或大小限制。长时间运行后，processed-keys.txt 会持续增长，每次 contains()
  调用都要全量读取文件。

  影响：
  - 启动时文件越大，replay 前的检查越慢
  - 极端情况下文件可能达到 GB 级别

  严重性：中等（生产环境长期运行会暴露）

  问题 8-C（中等）：FileBackedDeadLetterQueue.replay() 中 consumer 失败时 task 原地修改

  FileBackedDeadLetterQueue.java:59-62

  } catch (Exception ex) {
      task.setAttemptCount(task.getAttemptCount() + 1);
      task.setLastFailure(ex.getMessage());
      failedTasks.add(task);
  }

  FragmentPersistenceTask 使用 @Data（Lombok 生成 mutable setter），replay 时直接修改了 task 对象的字段。这些对象是从
  JSON 反序列化出来的，修改后写回 DLQ 文件——这是正确行为。

  但问题是：没有 max attempt count 限制。一个永远失败的任务会无限重试，DLQ 永远不会清空它。

  严重性：中等

  问题 8-D（低）：replay() 和 enqueue() 共用同一个 lock，replay 阻塞所有新 enqueue

  FileBackedDeadLetterQueue 的 synchronized(lock) 在 replay() 期间持有锁，整个 replay 过程中任何新的 enqueue()
  调用都会被阻塞。在 replay 大量积压任务时，异步持久化线程会被阻塞。

  严重性：低（MVP 可接受）

  评分：7/10
