阶段 1：修复 5 个已知问题（→ 8.8 分）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ ] 1. 修复 recency 24h 归零问题
    问题：recencyScore() 是线性衰减到 0，超过 24h 的片段全部归零，
          两天前和两周前在 recency 维度完全无差异，区分力消失。
    修复：改为对数衰减（log decay），超过 24h 后仍保留区分力。
    文件：MemoryFragment.java:75-79
    类型：算法

[ ] 2. recall 命中后刷新 lastAccessTime
    问题：HMC recall 使用 getAll(namespace) 返回列表，不更新
          lastAccessTime。刚被召回使用过的片段 recency 得分仍然很旧，
          容易被误淘汰。
    修复：HMC recall 改走 get(id) 而非 getAll()，确保被召回片段
          recency 得分即时更新。
    文件：HierarchicalMemoryController.java:162-166
          CaffeineHotStore.java:82-86
    类型：工程

[ ] 3. 候选集按 namespace 隔离
    问题：淘汰候选为 getAllFragments() 全局候选，多会话场景下，
          一个 namespace 的写入可能驱逐另一个 namespace 的热数据。
    修复：淘汰候选改为 getAllFragments(namespace)，禁止跨租户候选池合并。
    文件：HierarchicalMemoryController.java:220-224
    类型：隔离风险

[ ] 4. 候选池策略改为"按 token 密度"
    问题：预选"条目数前 10%"后再按 token 目标淘汰，当条目都很小时
          预选池可能不够，无法达到释放 token 目标，随后落到 Caffeine
          默认淘汰，策略不稳定。
    修复：废弃条目数前 10% 预选，改为按 score/tokenCount（价值密度）
          排序，确保释放量可稳定达标。
    文件：HierarchicalMemoryController.java:227-228
    类型：算法

[ ] 5. importance 动态更新机制
    问题：importance 默认值 0.5，业务没有主动标注时 γ*importance
          实际贡献有限，语义淘汰退化为"recency+similarity"。
    修复：在 recall / answer-grounded 回调中更新 fragment.importance，
          避免 γ 项长期贡献为零。
    文件：MemoryFragment.java:47-48
    类型：算法

阶段 2：可观测性 & 后悔信号（→ 9.2 分）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ ] 6. 写入 eviction decision log
    问题：现有实现无法回答"为什么这个片段被淘汰"，出问题无从排查，
          也无法积累数据用于后续优化。
    修复：每次淘汰前记录结构化日志，包含 fragmentId、各维度得分贡献
          （recency/similarity/importance 分项）、触发 namespace、时间戳，
          目标 100% 决策可追溯。
    文件：SemanticEvictionPolicy.java
    类型：可观测性

[ ] 7. 统计 Eviction Regret 指标
    问题：目前无法量化淘汰策略的决策质量，不知道有多少片段是"错误淘汰"。
    修复：记录被淘汰片段 ID，若在 TTL 窗口内从 L2/L3 再次被召回则计入
          "后悔"，建立 Regret 率监控，目标后悔率 <5%。
          （此指标也是阶段 4 在线学习的训练信号，必须先建立。）
    类型：质量指标

[ ] 8. 下沉链路幂等 & 可重放
    问题：异步下沉 L2/L3 失败时无重试保障，进程崩溃可能导致关键片段
          既从 L1 删除、又未成功写入 L2/L3，造成数据丢失。
    修复：L2/L3 写入加幂等 key，失败写入 dead-letter queue，
          支持重放；确保进程崩溃后无关键片段丢失，恢复成功率目标 100%。
    文件：CaffeineHotStore.java:42-49
    类型：可靠性

阶段 3：namespace 强隔离 & 依赖保护（→ 9.5 分）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ ] 9. 硬配额 + 弹性借用
    问题：无 namespace 级别配额，高频写入的 namespace 理论上可将所有
          其他 namespace 的热数据全部驱逐，多租户场景下公平性无保障。
    修复：每 namespace 设 hardQuota + softQuota，允许短时借用空闲容量
          但可被快速回收，任意时刻可证明 A 写爆不会清空 B 的核心热记忆。
    类型：多租户隔离

[ ] 10. Pin 机制 & 组淘汰
    问题：关键结论片段、中间推理节点可能被正常淘汰，导致推理链被切断，
          后续召回拿到的是碎片化片段而非完整上下文。
    修复：关键片段支持 pin(ttl) 短期不可淘汰；同一 reasoning chain
          的片段组内保持一致，要么一起保留，要么一起降级，不拆散推理链。
    类型：依赖保护

[ ] 11. 添加冗余度维度
    问题：语义高度相似的重复片段（cosine similarity >0.95）占用相同配额
          但价值边际极低，现有打分公式未考虑片段间的冗余关系。
    修复：对高相似度片段优先合并或淘汰副本，减少重复信息占用，
          同时可将"新颖性"作为保留得分的加分项。
    类型：算法

阶段 4：在线学习 & SLO 闭环（→ 10 分）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ ] 12. α/β/γ 在线权重学习
    问题：alpha/beta/gamma 固定值只能对某一类场景做到相对最优，
          coding、chat、search 三种场景下各维度的相对权重本来不同，
          手工拍参数无法自动适应业务变化。
    修复：引入轻量 bandit 或 LR，以"是否用于最终回答"和"Regret 信号"
          为反馈，按场景（coding/chat/search）训练不同参数 profile，
          让权重随业务自动收敛。（依赖阶段 2 的 Regret 统计作为训练信号。）
    类型：在线学习

[ ] 13. 影子模式评估新权重
    问题：直接上线新权重风险过高，可能导致召回质量短期大幅下降。
    修复：新权重先在影子流量上跑 Recall@nDCG 评估，稳定提升 ≥20%
          且持续 2 周后再切主流量，不达标自动回滚。
    类型：质量门禁

[ ] 14. 建立固定 SLO 基准集 & 告警
    问题：没有量化验收标准，无法客观判断系统是否达到生产级质量，
          也无法在回归时及时发现劣化。
    修复：建立以下 SLO 并配置告警：
          - Recall@nDCG 相比纯 Caffeine 提升 ≥20%，稳定 2 周
          - Eviction Regret 率 < 5%
          - 跨 namespace 核心片段误淘汰 = 0
          - store / recall p99 延迟劣化 < 10ms
          - 下沉链路恢复成功率 = 100%（故障演练通过）
          - 100% 淘汰决策有结构化原因日志
    类型：运维 / 验收终点
