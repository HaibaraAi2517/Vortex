# 2026-11-17 中文跨会话记忆基线

本轮用真实模型和真实 Vortex 服务测量当前实现，不在运行器中修补生产 SDK。已查阅的开发集轨迹暴露了三种不同问题：引用文本被误当作用户资料；同会话指代在抽取阶段丢失；事实已保存并召回，回答模型仍无法确定它属于用户。这些问题应分别修复，不能统一归因为向量召回不足。

首轮已跑完 300 个案例与方法组合，但 21 个组合出现模型调用异常，运行状态为 `completed_with_errors`。第二轮降低并发后遭遇持续 HTTP 402，在保存 287 个组合结果时主动中止，另有 13 个组合没有完成记录。两轮独立保存，没有覆盖或拼接最佳答案；目前还没有一轮全部无运行异常的完整基线。

首轮共记录 2073 次客户端模型调用尝试。26 次错误分属 13 次执行阶段、1 次裁判、7 次抽取和 5 次摘要更新，均记录为 `ModelError`，分布在 21 个组合。首轮没有记录 HTTP 状态，无法确定这些错误的具体原因，不能用第二轮发现的 HTTP 402 倒推首轮也因额度失败。

Vortex 首轮在最终提问前观测到 97 个案例的五字段快照，其中 89 个全部通过严格状态/子串检查；485 个字段中 475 个通过。有 4 个本应缺席的字段成为 `ACTIVE`。这些是结构诊断，不是语义写入准确率。

最终问题前后均有快照的 Vortex 案例为 95 个，其中 1 个发生字段变化。开发集实际观测 56 个、变化 0 个，所以没有开发集问句可归因为“新事实写入”或“无意义 revision 增长”。测试集只报告 39 个观测、1 个变化，不打开其具体轨迹来指导本轮改动；不能仅凭这个计数断言变化的性质。

首轮 Vortex 开发集中的可判质量失败集中在归属、指代和撤回后回答：归属类 4/6、指代类 3/6、撤回类 5/6，其余已完整执行的基础保存、更正、时间、临时计划、局部属性修改和干扰类均为 6/6。拒答类受到运行异常影响，不能用缺失判分判断其质量稳定性。

## 第二轮因 HTTP 402 中止

第二轮于北京时间 2026-11-17 01:27:05 启动，并发从 6 降到 2；01:35:39 由主代理显式终止匹配的评测进程，停止进一步模型调用。这一轮不是运行器自动停止。相较首轮，当时的运行器只增加了安全的 HTTP 错误状态元数据。两轮的模型配置、数据、生产 SDK、BGE 与相关本地制品指纹保持一致，变化的源码指纹仅为运行器。

保存的 287 个组合中，123 个有有效裁判，164 个记录了执行阶段 `ModelError`、`http_status=402`。HTTP 402 表明模型供应商的付款或额度条件未满足；本次没有充值或切换模型。剩余 13 个组合没有完成记录，因此第二轮不能作为完整质量对照。

第二轮 checkpoint 仍保留原始 `status: running`，因为进程是在运行中被终止，没有执行正常收尾。它不是服务仍在运行的证明，也未被改写成成功。提交版摘要根据独立停机证据将该次运行标为 `interrupted_http_402`，并保留原始状态、287 条结果与未完成分母。停机记录确认 `source_unchanged=true`。

两轮结束后，评测器才新增共享 `RunControl`：识别 HTTP 401/402 后停止派发新案例，并在后续模型调用入口阻止继续请求，保留在途案例证据和 pending 分母。该保护通过离线测试验证，未用于重新发起付费复测，也未参与上面两轮；不能把第二轮停在 287 条解释成新增机制当时已自动生效。生产 SDK 和原始报告未因此改写。

这次中止没有提供“改进后成绩”；生产记忆逻辑本来也没有修改。以下产品归因仍依据首轮开发集原始轨迹，不把第二轮成功答案替换进首轮分数。干净的完整复测仍需可用的同模型 API 访问，之后应选择新输出路径重新完整运行。

## 成功抽查与指标边界

额外查阅两条开发集成功轨迹，与自动裁判结论一致：`partial_01--vortex.json` 将普通牛奶改成燕麦奶后，事实 v2 和最终回答均保留“无糖拿铁”；`retraction_01--vortex.json` 把不再住北京的城市事实置为 `RETRACTED` v2，新会话召回为空并明确回答当前城市未知。两例最终问句均未改变字段版本或内容。此抽查不代表全部自动判分已经人工验证。

事实检查是终态的状态和字面子串诊断。例如包含“糖”不能证明无糖极性正确；本轮没有逐轮写入金标准，不将它称为语义写入准确率。`stale_claim` 也包含本数据明确列出的错误主体或无依据当前断言，不只表示旧版本泄漏。无记录时不猜测、已知时不无谓拒答，是两个不同要求。

SDK 适配器没有返回供应商 token usage，因此调用量和时延可以报告，token 与金额保持未知。并发案例耗时之和不等于真实墙钟时间。基础设施失败、没有有效裁判的案例以及最终问题导致的状态变化，都应保留在报告中，不能从分母静默删掉。

## 下一轮改动的顺序

1. 抽取时传入有限的同会话用户原话，解析指代；继续排除助手生成内容作为新增事实证据。
2. 对小说、引用、转述先确定说话者和事实主体，保存足够的来源上下文；不能仅凭证据子串存在就准许写入用户档案。
3. 回答上下文保留字段名、当前状态与用户归属；明确属性问题可直接读取对应当前事实。对空证据仍需检查猜测行为。
4. 修正用户可见的写入/撤回结果呈现，并增加中间轮错误验收。

这些是依据本次开发集提出的后续候选，本轮未实施。抽查的局部咖啡属性更新已经正确，不能预先把原子字段拆分当作本次主要瓶颈。应先对照开发集失败修复，再用同一冻结数据版本复测；如果根据测试集具体答案调参，应另建留出集。

本报告只描述这 100 个项目自建合成场景、当前代码、一次带异常的完整尝试和一次中止复测。它不是通用准确率、LongMemEval 成绩、Codex/Claude 原生记忆对比或竞品排名，也不是外部用户已经可用的证明。
